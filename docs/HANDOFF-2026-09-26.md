## 1. 사용자와 작업 방식

- 1인 학습자다. GitHub `Jongkwang131`. **학습이 1순위이고 앱은 2순위.** 배우려는 것은 실무 Git 흐름, Jira, 멀티에이전트 하네스, 모델 라우팅이다.
- **모든 보고는 한국어로 한다.** 각 단계에 "실무 관점" 설명을 붙인다. 사용자가 명시적으로 요청했다.
- 선택지는 **번호 + 추천**으로 제시하고, **한 메시지에 질문은 하나**만 한다. 결정된 것은 다시 논의하지 않는다.
- **백엔드와 인프라 기초 용어를 잘 모른다.** 도메인, 스테이징 같은 용어는 쓰기 전에 비유로 먼저 설명한다. 예: 링크를 누르면 벌어지는 일 순서대로.
- 사용량: 전체 사용량은 여유가 있다. **Fable은 빨리 닳으니 드물게** 쓴다. **설계 단계에서는 ultracode를 켜 두기를 원한다.**
- 이전 앱 choreography가 멈춘 이유(사용자 본인의 말):
  1. 스펙을 확정하지 않고 만들면서 계속 수정했다.
  2. Git을 제대로 쓰지 않아 학습이 되지 않았다.
  3. AI에게 "이거 해"만 시키는 느낌이었다.

- **Must**
  - 리더 카카오 로그인. 작품 만들기·목록·열기
  - 서버 자동 저장: 저장 번호, 충돌 시 409(E2), 창을 닫을 때 전송, 연결이 끊기면 임시 저장(E3)
  - 무대 그리드, 댄서 추가·이름(색은 자동 배정), 드래그 + 스냅(항상 켜짐), 대형 추가·삭제
  - 로컬 팀 파일, 타임라인(대형 블록, 이동 구간, 카운트 단위로 붙음), 재생·정지·탐색, 보간
  - BPM 숫자 입력 + "지금 위치를 1-1로" + 카운트 표시
  - 공유 링크(복사, 휴대폰 기본 공유창), 뷰어 + "나는 누구" 강조, Wake Lock, 카톡 인앱 안내
- **Should**
  - 기존: 편집자 초대 + 편집 잠금(E5), 멀티선택·정렬, 동선 화살표·잔상, 대형 메모(뷰어 표시 포함), 파형, 로컬 영상 나란히 보기, 팀 파일 일치 확인(E4), OG 미리보기 카드, 홈 화면 설치 안내
  - Must에서 내림:
    - undo·redo. 그동안 대형 삭제는 확인 창으로 대신한다
    - 핀치 줌·팬. 스파이크에서 폰 세로 편집이 불가하다고 판정되면 Must로 올린다
    - 탭 템포, 링크 재발급(E1)
    - 0.5·0.75배속, 미러, 의사 전체화면, 싱크 보정, 카운트만 모드
    - 작품 삭제
    - 가로·태블릿 전용 배치(③-T, ③-L, ⑧-L, ⑨-L). Must는 배치 하나를 화면에 맞춰 늘리는 것까지다
  - 새로 추가: 댄서 삭제
- **Could**
  - 기존: 유튜브 임베드, PDF 내보내기, 오프라인 캐시, 크루 템플릿, 시점 뒤집기, 대형별 색 덮어쓰기, 음원을 영상으로 변환
  - 새로 추가:
    - 작품 이름 변경·복제, 댄서 색 변경, 스냅 끄기
    - 대형 복제, 대형 이름 변경, 시간 숫자 입력, 대형 사이 끼워 넣기
    - 이전·다음 대형 점프, 1-1 ±10ms 미세 조정, 에디터에서 보기로 전환
    - 뷰어의 "다음 동작 안내", 팀 파일 기억, 카카오 SDK 공유 버튼
- **Won't**
  - 기존: 실시간 동시 편집, 서버 미디어 저장, 일정·알림, 스테이징(입퇴장·소품·조명), 곡선 경로, 영상에서 대형 자동 생성
  - 새로 추가:
    - 작품 끝 지정. 규칙으로 대신한다: 파일 길이, 파일이 없으면 마지막 대형 + 4초
    - 대형 순서 바꾸기
    - 영상 움직임 기반 전환 시점 제안
- Figma의 Must 실선·Should 점선 표시는 아직 옛 목록 기준이다. **범위의 원본은 이 목록(이후 스펙)**이다. Figma 표시는 비주얼을 다듬는 스프린트 때 맞춘다.

**설계 ③ 데이터 모델 (확정, 하이브리드)**
- 원칙: 늘 같이 읽고 같이 저장하는 데이터는 문서 한 덩어리로 둔다. 따로 조회해야 하거나 권한·관계가 걸리는 데이터는 표로 둔다. ①에서 대략 적은 "표 4개(작품·댄서·대형·편집자)"를 이것으로 대체한다.
- 테이블은 전용 스키마(`public` 아님)에 둔다.
  - `app_user(id = Supabase 사용자 id, display_name, created_at)`
  - `project(id, owner_id → app_user ON DELETE CASCADE, title, share_token UNIQUE(128비트 이상), revision, schema_version, content JSONB, created_at, updated_at)`
- `content` 형식 1판:
  - `grid{cols,rows,backstageCols}`
  - `tempo{bpm,firstBeatMs}|null`
  - `teamFile{name,durationMs}|null`
  - `dancers[{id,name,color}]`
  - `formations[{id,startMs,transitionInMs,positions{dancerId:{x,y}}}]`
- 이전 앱의 규칙을 이어받는다: 좌표는 0~1(백스테이지는 −0.1~1.1), 시간 원본은 ms, 순서는 startMs 순, 대형 구간 겹침 금지, 새 댄서는 백스테이지에 놓는다.
- 넣지 않은 필드: 대형 이름·메모·색, 스냅, 뒤집기, 작품 끝, countsPerPhrase, 팀 파일 오프셋. 나중에 선택 필드로 추가한다.
- 서버에 두지 않는 것: 싱크 보정(기기 저장소), "나는 누구"(`?me=댄서id`), 팀 파일.
- 자동 저장은 `UPDATE … WHERE id=? AND revision=?` 한 줄이다(낙관적 잠금). 바뀐 줄이 0개면 409를 돌려준다.
- 서버는 형식·범위·크기를 검사한다.
- 문서 형식이 바뀌면 `schema_version`을 올리고, 서버가 읽을 때 새 판으로 올린다.
- 작품 목록의 요약(댄서 수, 대형 수, 곡 길이)은 문서에서 계산한다.
- Should와 v2는 나중에 표를 붙인다: `project_editor`, 잠금 칸 2개, `team` + `project.team_id`.

**설계 ④ API 계약 초안 (확정)**
- Must 엔드포인트 6개:
  - `GET /api/projects`: 목록 요약
  - `POST /api/projects {title, content}`: 201 `{id, revision:1, shareToken}`
  - `GET /api/projects/{id}`
  - `PUT /api/projects/{id} {baseRevision, content}`: 200 `{revision}`. 충돌이면 409와 함께 최신 `{revision, content}`를 돌려준다
  - `GET /api/share/{token}`: 익명. `{title, ownerName, content}`. 없으면 404
  - `GET /api/health`: DB를 실제로 조회한다
- 인증은 Supabase 토큰을 Bearer로 받는다. 토큰이 없거나 틀리면 401이다.
- 남의 작품이면 404를 돌려준다(존재를 숨긴다).
- 가입 API는 없다. 첫 `POST` 때 JWT 닉네임으로 `app_user`를 upsert한다.
- 첫 문서는 프론트가 만들고, 서버는 같은 검사로 확인한다.
- 409 응답에 최신본을 싣는다. "덮어쓰기"는 최신 revision을 기준으로 다시 PUT하면 된다. 강제 옵션은 두지 않는다.
- **같은 내용을 다시 보내면 200이다.** 응답이 유실된 뒤의 재시도를 대비한 규칙이다.
- 창을 닫을 때: keepalive는 64KB 제한이 있다. 그래서 기기 저장소에 먼저 쓰고, 전송은 최선을 다해 시도하는 수준이다.
- 오류는 RFC 9457 Problem Details로 돌려준다.
- `content`의 스키마는 `openapi.yaml`에 둔다.
- 공유 조회에는 IP당 요청 수 제한을 둔다.
- Should: `DELETE` 작품, `POST …/share-token` 재발급, 편집자·잠금, OG `/s/{token}` HTML.
- ⚠️ OG HTML을 어디서 렌더링할지 기록이 갈린다. 인계서 4절은 Cloudflare 함수, 메모리는 Spring이다. OG 작업에 착수할 때 정한다.

**설계 ⑤ 핵심 흐름·예외 (확정)**
- **자동 저장:**
  - 변경은 항상 기기 저장소에 먼저 쓴다(선기록).
  - 1초 디바운스 후 `PUT`한다. 동시에 보내는 요청은 1개다.
  - 성공하면 기기 저장소를 비운다.
  - 작품을 열 때 남은 변경이 있으면: 기준 판이 서버 판과 같으면 복구해서 올린다. 서버가 더 새것이면 E2로 간다.
- **편집 규칙:**
  - 새 댄서는 모든 대형의 백스테이지(왼쪽 열 위부터)에 놓는다.
  - 새 대형은 마지막 대형을 복사한다. +8카운트(템포가 없으면 +4초), 이동 2카운트(1초).
  - 대형 삭제는 확인 창을 띄운다. **첫 대형은 삭제할 수 없다.**
  - 블록은 카운트 단위(템포가 없으면 0.1초)로 스냅한다. 겹치면 클램프한다.
  - 재생 중에는 편집을 잠근다. 백그라운드로 가면 정지한다.
- **재생:**
  - 팀 파일은 `<video>` 요소 하나로 재생한다(음원도 같은 요소).
  - `currentTime`을 `performance.now()`로 보간하고, rAF마다 `poseAt(t)`를 계산한다.
  - 작품 끝은 파일 길이다. 파일이 없으면 마지막 대형 + 4초다.
- **뷰어:**
  - 파일이 없어도 타임라인 탐색은 된다. 재생 버튼만 파일을 요구한다.
  - 재생하면 Wake Lock을 요청하고, 화면이 다시 보이면 재요청한다.
  - 자동 갱신은 없다. 새로고침해야 최신이 보인다.
- **예외(Must):**
  - E2: [최신 불러오기] / [덮어쓰기].
  - E3와 그 밖의 저장 실패는 모두 같은 처리다(기기 보관 + 배너 + 재시도).
  - 401: 로그인으로 보낸다. 기기 저장소는 유지되므로 다시 로그인하면 복구된다.
  - 에디터 404: 목록으로 보낸다.
  - **잘못된 공유 링크 404: 일반 문구 화면. 오타·잘린 링크 대비라 Must로 둔다.** E1의 재발급 문구는 Should다.
  - 재생 불가 파일: 안내 문구를 띄운다.
  - Wake Lock 거부: 무시한다.

**설계 ⑥ 테스트·보안 (확정)**
- **테스트 층:**
  - Vitest 단위 테스트: 도메인 계산(이전 앱 테스트 케이스를 이식) + 자동 저장 장치(가짜 서버 함수 주입).
  - Spring 통합 테스트: Testcontainers Postgres + spring-security-test 가짜 JWT로 API 6개의 401·404·409·같은 내용 200·400을 검사한다.
  - 계약 일치: `openapi.yaml`에서 openapi-typescript(FE)와 openapi-generator(BE 인터페이스, bean validation)를 생성해 컴파일로 강제한다.
  - Playwright E2E 스모크 1개: 스테이징 대상, develop 배포 후 실행, 비차단.
  - 실기기 체크리스트: 5개 환경(iOS Safari, iOS 카톡, Android Chrome, Android 카톡, 삼성 인터넷)에서 싱크 3분 ±50ms, 토큰 20개 부드러움을 확인한다. 릴리스 PR 전에 돈다. eruda는 미리보기 빌드에만 넣는다.
- **E2E 인증:** 스테이징 Supabase에만 이메일 로그인과 테스트 계정을 둔다(앱에 뒷문 없음). 운영은 카카오만 쓴다.
- **CI:** 영역별 잡은 경로 조건으로 돌리고, 필수 체크는 항상 도는 `ci-ok` 하나만 둔다.
- **보안:**
  - JWKS 검증(alg·iss·aud=authenticated, ES256이면 `jws-algorithms`).
  - 모든 쿼리에 `owner_id` 조건.
  - 전용 스키마 `app`, Flyway·앱 역할 분리. Data API에 노출하지 않고 공개 역할 권한은 0이다(셋업 때 쿼리로 검증).
  - 공유 토큰은 128비트 SecureRandom. `/api/share/*`는 IP당 분당 60회(메모리 카운터). `noindex` + robots.txt.
  - 입력 검증:
    - 요청 크기는 256KB 이하.
    - 좌표 −0.1~1.1, 시간 0~30분, BPM 20~300.
    - 제목 100자, 이름 20자, 댄서 50명, 대형 500개.
  - React escape만 쓰고 `dangerouslySetInnerHTML`은 금지.
  - CORS: 운영은 운영 주소만. 스테이징은 스테이징 + `*.pages.dev` + localhost.
  - PR 미리보기는 스테이징 API·DB를 쓴다. 로그인 redirect 와일드카드는 스테이징에만 둔다.
  - 비밀값은 Secrets·env에 두고 push protection을 켠다.
  - 카카오에서는 닉네임만 받는다.
  - pg_dump를 비공개 S3에 올리고 복원을 1회 연습한다.
- **범위 보정:** 개인정보 처리방침 정적 페이지 = **Must**(개인정보보호법 제30조). 회원 탈퇴 = Should이고, 파일럿 중에는 수동으로 처리한다(DB 삭제, Supabase 사용자 삭제, 카카오 unlink).

**설계 ⑦ 로드맵 (확정)**
- 마일스톤은 날짜가 아니라 시연 가능한 상태로 끝낸다. 마일스톤 하나 = Jira 에픽 하나, 스프린트는 1주다.
  - **M0 준비·스파이크(1~2):** 셋업과 버리는 스파이크. 스파이크 결과표를 보고 스펙을 갱신한다.
  - **M1 걸어 다니는 뼈대(1~2):** 로그인→작품 생성→목록을 스테이징에서 확인하고, 첫 운영 릴리스를 연습한다.
  - **M2 에디터(2~3):** 음악 없이 대형 편집, 새로고침 유지, E2.
  - **M3 시간과 음악(2):** 실제 곡으로 포메이션 완성.
  - **M4 공유·뷰어(1~2):** 시나리오 전체가 스테이징에서 실기기 5종 통과.
  - **M5 파일럿(1+운영):** 완료 시나리오 달성.
- Should의 순서는 파일럿 피드백으로 정한다. 예외: 스파이크에서 Must로 올린 것.
- 스프린트 1이 끝나면 벨로시티를 재서 재추정한다.
- Must 어림은 약 40~70 작업일이다. 파일럿 가능 시점은 2027년 1월 말~3월 초이고, 가장 유력한 것은 2월(겨울방학 연습기)이다. 대안은 3월이다. 사용자가 동아리 일정을 확인해야 한다.
- 서비스 이름은 M0 셋업 전까지 정하면 된다.

## 3. 아직 정하지 않은 것

- **서비스 이름.** 이것에 따라 Jira 키, GitHub 조직과 레포 이름, 도메인이 정해진다. 셋업 전에만 정하면 된다.
- **파일럿 시점.** 12월 중순은 기말고사와 겹친다. 겨울방학 연습기와 3월 신입 모집기 중에서 동아리 일정과 맞춰 정해야 한다.
- **Lightsail 서울 가격.** 셋업할 때 확인한다.

## 4. 스펙에 반드시 반영할 항목 (조사에서 나온 제약과 누락 작업)

> ⚠️ **역사 기록.** 이 절의 내용은 이미 스펙에 반영됐다. 일부 값(예: 58~100 작업일, 2027년 4월, OG 렌더링 위치)은 스펙과 다르다. **구현에 쓰지 않는다.**

- **카톡 인앱 브라우저**
  - 구글 OAuth가 차단된다. 카카오 로그인을 쓰고, 멤버 경로에는 로그인을 두지 않는다.
  - 홈 화면 추가, 푸시, 서비스 워커를 쓸 수 없다.
  - Wake Lock과 인라인 영상 재생은 실기기 스파이크로 확인한다.
  - 외부 브라우저로 여는 공식 방법이 없다. `kakaotalk://web/openExternal`은 비공식이다.
  - 저장소가 환경마다 분리된다. 그래서 "나는 누구" 선택은 URL(`?me=`)에 둔다.
  - OG 태그는 서버에서 렌더링해야 한다. Cloudflare Pages Function을 쓴다.
- **아이폰:** 요소 전체화면이 불가능해서 의사 전체화면으로 대체한다. 화면 방향 고정이 불가능하다.
- **오디오 재생:**
  - `<audio>` 또는 `<video>` 요소로 재생한다. Web Audio는 무음 스위치에 걸리고, 느린 재생에서 음정 유지 문제가 있다.
  - `currentTime`은 `performance.now()`로 보간한다.
  - 싱크 오프셋의 기본값은 0이다. 이중 보정에 주의한다.
- **가로 모드:** 무대가 2:1 비율이라 가로가 오히려 잘 맞는다. 가로 전체화면을 추천 연습 자세로 둔다.
- **백엔드와 DB:**
  - Supabase JWKS가 ES256일 수 있다. 그 경우 `jws-algorithms`를 설정한다.
  - JDBC는 Session pooler 5432를 쓴다.
  - Flyway 소유자 역할과 앱의 최소 권한 역할을 분리한다.
  - 새 Supabase 프로젝트는 public 스키마를 자동으로 노출하지 않는다. 그래도 GRANT가 걸리지 않았는지 확인한다.
  - Supabase Free는 1주 동안 활동이 없으면 일시정지되고, 자동 백업이 없다. keep-alive와 백업 cron을 둔다.
- **데이터:**
  - 프로젝트 문서에 schemaVersion을 둔다.
  - 자동 저장은 409 충돌 UX, 창을 닫을 때 keepalive flush, 오프라인 임시 저장을 포함한다(Must).
  - 회원 탈퇴 시 카카오 연결을 끊는다.
  - 공유 토큰은 128비트 이상이고 rate limit을 건다.
  - 접근성 기본을 지킨다. 색에만 의존하지 않고, 확대를 막지 않는다.
- **CI:**
  - paths 필터와 required check를 함께 쓰면 체크가 pending에 갇힌다. 항상 도는 집계 잡으로 해결한다.
  - E2E를 위한 테스트 인증 경로를 둔다. 카카오 OAuth는 자동화할 수 없다.
- **개발 환경:**
  - Windows라서 Docker Desktop(WSL2)과 JDK를 쓴다.
  - Mac이 없으니 iOS 디버깅은 eruda나 vConsole로 한다.
  - 테스트 기기 확보 계획이 필요하다.
- **환경 전략:** 프리뷰와 스테이징이 어느 API와 DB를 쓰는지 정한다. CORS, Supabase redirect 와일드카드도 함께 정한다.
- **예외 상태:**
  - Must: E1 만료 링크, E2 저장 충돌 409, E3 연결 끊김
  - Should: E4 파일 길이 불일치, E5 편집 중
- **초기 추정:** 84개 이상 태스크, 58~100 작업일. Spring을 쓰는 비용은 +3~7일(약 5%). 학기 중 페이스라면 MUST 파일럿은 2027년 4월 초가 가장 유력하다. 첫 스프린트 벨로시티를 잰 뒤 재추정한다.
