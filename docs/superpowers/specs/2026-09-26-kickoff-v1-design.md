## 0. 이 문서의 규칙

- **이 스펙이 v1 범위의 원본이다.** 인계 문서, Figma, 대화 기록과 내용이 다르면 이 문서를 따른다.
  - Figma의 Must 실선·Should 점선 표시와 일부 문구는 옛 범위 기준이다. 비주얼을 다듬는 스프린트에서 맞춘다.
- **스펙은 PR로만 바꾼다.** 순서는 이렇다:
  1. 실기기 피드백과 새 아이디어는 먼저 GitHub 이슈로 올린다.
  2. 트리아지한다.
  3. 필요하면 스펙을 고치는 PR을 낸다.
  4. 그다음에 구현한다.
  - 이전 앱 choreography가 멈춘 첫 번째 원인이 "만들면서 스펙을 계속 고쳤다"였다. 이 규칙은 그것을 막기 위한 것이다.
- **범위 판정 기준 (멘토 조언: "기획 단계에서는 최대한 덜어내라"):**
  - **Must:** 빠지면 §1.3 완료 시나리오가 깨지는 것만 넣는다.
  - 크기가 작다거나 이전 앱에 있었다는 사실은 기준이 아니다.
  - 대신할 수단이 있으면 Should 이하로 내린다.
  - **데이터 손실 방지, 보안, 법적 의무는 덜어내지 않는다.**
- **규칙은 한 곳에만 적는다.** 다른 절에서는 그 절을 가리키기만 한다. 예를 들어 문서 검증 규칙은 §5.3에만 있다.
- 항목 ID(M-xx, S-xx 등)는 Jira 스토리와 GitHub 이슈에서 참조한다.

## 1. 제품

### 1.1 한 줄 정의

리더가 무대 위에 포메이션을 만들고 링크 하나로 공유한다. 멤버는 각자 폰에서 **자기 동선을 음악에 맞춰** 확인한다.

### 1.2 사용자

| 사용자 | 하는 일 | 로그인 |
|---|---|---|
| 리더(편집자) | 작품 만들기, 대형 편집, 타이밍 맞추기, 공유 | 카카오 로그인 |
| 멤버(보는 사람) | 링크 열기, 자기 이름 고르기, 음악과 함께 동선 보기 | 없음 |

- 파일럿 대상은 학교 댄스 동아리 임원진이다. 기기는 아이폰과 안드로이드가 섞여 있다.
- 공유 링크는 주로 카카오톡 단톡방으로 퍼진다.
- **이용 대상은 만 14세 이상이다(§9.4).**

### 1.3 완료 시나리오 (v1의 닻)

> **임원 1명이 실제 곡으로 포메이션을 완성해 공유한다. 임원 3명 이상이 각자 폰에서 음악과 함께 자기 동선을 확인한다.**

v1은 날짜가 아니라 이 시나리오를 달성했을 때 끝난다. 마감은 없다.

### 1.4 v1에서 하지 않는 것과 이후 비전

- **v2 이후 비전:** 동아리 종합 앱. 팀별 일정 취합 → 연습 일정 → 알림·공지.
  - v1은 데이터 구조에서만 이 방향을 막지 않는다. 방법은 §5.5에 있다.
- **음원과 영상 파일은 서버에 올리지 않는다.** 서버가 상업 음원을 배포하면 저작권 전송권 침해 위험이 크기 때문이다.
  - 파일은 각자 기기에 있는 로컬 파일을 쓴다. 팀이 파일 하나를 정한다(mp4 권장).
  - **앱 문구와 파일럿 안내는 파일을 구하거나 주고받는 방법(예: 단톡방 전송)을 안내하지 않는다.** ⑥의 문구는 "팀에서 정한 파일을 이 기기에서 골라 주세요. 파일은 이 기기 밖으로 나가지 않아요"로 쓴다.

### 2.5 이전 앱(choreography)과의 관계

기능 동등성을 점검했다. 대상은 specs 01~04, 화면 코드, Figma 26개 프레임이다.

- **이어받는 도메인 설계:**
  - 0~1 정규화 좌표와 그리드 안 백스테이지 열
  - 시간 원본은 ms, 카운트는 표시용
  - Formation(startMs, transitionInMs)과 poseAt 보간
  - K-pop 카운트 표기("3-5")
  - 새 댄서 백스테이지 배치, 겹침 금지 제약, 이동 구간 편집 잠금
  - 유틸 경계값 테스트 케이스
- **바뀐 것:**
  - 로컬 SQLite → 서버 저장(§5)
  - 음원을 앱 내부로 복사 → 각자 기기의 팀 파일
  - 리더 기기 전체화면 재생 → 멤버 각자의 뷰어
  - 크루 관리 화면 → Could(크루 템플릿)
- **제거한 것:** §2.3과 §2.4에 적었다.

## 3. 아키텍처

### 3.1 구성

```
[브라우저: React + Vite SPA, TypeScript]  ── Cloudflare Pages
      │  (1) 카카오 로그인 ──▶ [Supabase Auth] ──▶ JWT 발급
      │  (2) Bearer JWT로 API 호출
      ▼
[Caddy] ─▶ [Spring Boot API (Java)]  ── AWS Lightsail 서울 VM (Docker)
      │  JWKS로 JWT 검증
      ▼
[Postgres]  ── Supabase 서울 (DB 호스팅만 사용, 스키마는 직접 설계)

팀 파일(음원·영상)은 각자의 기기 밖으로 나가지 않는다.
```

- **웹앱(PWA)은 하나만 만든다.** 모바일 퍼스트이고 터치를 우선한다. PC 브라우저에서도 열리지만 최적화 대상은 아니다.
- **Supabase는 로그인(카카오)과 Postgres 호스팅에만 쓴다.** Data API는 쓰지 않는다(§9.2).
- **API 도메인은 Cloudflare 프록시를 끈다(DNS only).** 그래야 Caddy가 실제 클라이언트 IP를 본다(§9.3).
- **모노레포:** `web/`, `api/`, `contract/openapi.yaml`, `docs/`.

### 3.2 환경

| 환경 | 웹 | API·DB | 브랜치 |
|---|---|---|---|
| 로컬 | Vite dev server | 로컬 Spring + Docker Postgres | — |
| PR 미리보기 | Cloudflare Pages preview (`<hash>.<pages프로젝트>.pages.dev`) | **스테이징** API·DB | PR |
| 스테이징 | 스테이징 도메인 | 스테이징 컨테이너 + Supabase 스테이징 프로젝트 | `develop` |
| 운영 | 운영 도메인 | 운영 컨테이너 + Supabase 운영 프로젝트 | `main` |

**운영 작업**

- **배포:** GHCR 이미지를 GitHub Actions가 SSH로 교체한다.
- **cron은 Lightsail VM의 crontab에서 매일 돈다.** GitHub Actions schedule은 쓰지 않는다. 공개 레포는 60일 동안 활동이 없으면 schedule이 꺼지기 때문이다.
  - keep-alive: 운영과 스테이징 **둘 다** `GET /api/health`를 호출한다.
  - 백업: **운영만** `pg_dump -n app`으로 떠서 비공개 S3에 올린다. 버킷에는 30일 뒤 자동 삭제되는 수명주기 규칙을 건다.
  - 백업 감시: 백업 스크립트는 S3 업로드까지 성공한 경우에만 마지막에 healthchecks.io(무료) 핑을 보낸다. 핑이 하루 넘게 오지 않으면 운영자에게 메일이 간다. 수명주기 규칙이 오래된 백업을 지우므로, 백업이 조용히 멈추면 30일 뒤 복원할 파일이 없어지기 때문이다. 핑 URL은 VM 환경변수에만 둔다.
- **AWS 예산 알림을 설정한다.**
- **Supabase:** 무료 플랜 2개를 쓴다(운영, 스테이징).

## 5. 데이터 모델

### 5.1 원칙

**늘 같이 읽고 같이 저장하는 데이터는 문서 한 덩어리로 둔다. 따로 조회하거나 권한·관계가 걸리는 데이터는 표로 둔다.** 안무 내용은 항상 통째로 읽고 통째로 저장하므로 JSONB 문서 하나에 담는다.

### 5.2 테이블 (스키마 `app`, Flyway로 관리)

```sql
CREATE TABLE app.app_user (
  id            uuid PRIMARY KEY,          -- Supabase 사용자 id (JWT sub)
  display_name  text NOT NULL,             -- 카카오 닉네임 (§6 규칙 3)
  created_at    timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE app.project (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  owner_id     uuid NOT NULL REFERENCES app.app_user(id) ON DELETE CASCADE,
  title        text NOT NULL CHECK (char_length(title) BETWEEN 1 AND 100),
  share_token  text NOT NULL UNIQUE,       -- 128비트 이상 무작위, base64url
  revision     bigint NOT NULL DEFAULT 1,  -- 저장 번호, 저장마다 +1 (낙관적 잠금)
  content      jsonb NOT NULL,             -- 안무 문서 (§5.3). 형식 번호 v를 안에 담는다
  created_at   timestamptz NOT NULL DEFAULT now(),
  updated_at   timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX project_owner_updated ON app.project (owner_id, updated_at DESC);
```

- DB 역할은 환경마다 한 번 **수동으로** 만들고, 비밀번호는 비밀값 저장소에 둔다(§9.2). Flyway 마이그레이션에는 권한(`GRANT`, 이후 표에도 적용되는 `ALTER DEFAULT PRIVILEGES`)만 넣는다.

### 5.3 `content` 문서 (형식 1판) — 검증 규칙의 원본

```json
{
  "v": 1,
  "grid":     { "cols": 16, "rows": 8, "backstageCols": 1 },
  "tempo":    { "bpm": 118.0, "firstBeatMs": 8500 },
  "teamFile": { "name": "fall_opening_v3.mp4", "durationMs": 201000 },
  "dancers":  [ { "id": "<uuid>", "name": "서연", "color": "#E4572E" } ],
  "formations": [
    { "id": "<uuid>", "startMs": 0, "transitionInMs": 0,
      "positions": { "<dancer id>": { "x": 0.5, "y": 0.8 } } }
  ]
}
```

| 필드 | 규칙 |
|---|---|
| `v` | 문서 형식 번호. 지금은 1이다(§5.5) |
| `grid` | cols 6~24, rows 4~16. `backstageCols`는 v1에서 1로 고정한다(바꾸기는 Could). 그리드는 표시와 스냅용일 뿐이라, 값을 바꿔도 좌표는 그대로다 |
| 좌표계와 백스테이지 | 좌표 0~1은 **그리드 전체**(cols에 백스테이지 열이 포함된다)이고, 원점은 좌상단이다. 백스테이지 구역은 두 곳이다. 하나는 그리드 안 좌우 끝 열(`x < 1/cols` 또는 `x > 1 − 1/cols`)이고, 다른 하나는 0~1 밖의 띠다 |
| `positions` | x, y는 **−0.1~1.1**이다 |
| `tempo` | 없으면 `null`이다. BPM은 20~300이고 소수 첫째 자리까지다. `firstBeatMs`는 1-1 카운트의 절대 ms다. 한 프레이즈는 8카운트로 고정한다 |
| `teamFile` | 리더가 고른 파일의 이름(1~200자)과 길이만 저장한다. 없으면 `null`이다 |
| `dancers` | 배열 순서가 표시 순서다. id는 클라이언트가 `crypto.randomUUID()`로 만들고 **중복이 없다**. 이름은 1~20자, 최대 50명이다. 색은 10색 팔레트(이전 앱)에서 차례로 자동 배정한다 |
| `formations` | **startMs가 엄격히 증가한다**(n ≥ 2이면 `F(n).startMs > F(n−1).startMs`, 같은 값은 안 된다). 최대 **200**개다. id는 **중복이 없다**. 표시 이름은 순서대로 "대형 N"이다(저장하지 않음). 첫 대형은 startMs=0, transitionInMs=0이다. 제약: `F(n).startMs − F(n).transitionInMs ≥ F(n−1).startMs`. 모든 대형의 `positions` 키는 **정확히** `dancers`의 id 집합과 같다 |
| 시간 | 모든 시간(`startMs`, `transitionInMs`, `firstBeatMs`, `durationMs`)은 **정수** ms이고 0~1,800,000(30분)이다 |
| 카운트 (표시용) | `beat(t) = floor((t − firstBeatMs + 1) · bpm / 60000)`. +1ms는 정수화한 격자 시각과 부동소수점 오차를 흡수하는 여유다. `beat ≥ 0`이면 `"{floor(beat/8)+1}-{beat mod 8 + 1}"`로, 아니면 m:ss.d로 표시한다. 예: bpm 118, firstBeatMs 8500, t=10025 → "1-4". bpm 84, firstBeatMs 8500, t=13500 → "1-8" |
| 박 격자 | `gridMs(k) = Math.round(firstBeatMs + k · 60000 / bpm)`. k는 음수일 수 있다 |

- **클라이언트가 문서에 쓰는 값은 항상 위 규칙을 통과해야 한다.** 규칙을 지키는 방법은 §7.3에 있다. 이 규칙을 어긴 저장은 클라이언트 버그로 본다.
- **크기:** 상한을 꽉 채운 문서(50명 × 200개, 24열, 이름 20자)는 약 0.7MB로 추정한다. 요청 한도(1MB, §6 규칙 7) 안에 든다.

### 5.4 서버에 저장하지 않는 것

- **싱크 보정값(S-17):** 기기마다 다르므로 기기 저장소에 둔다.
- **"나는 누구":** 주소의 `?me=댄서id`에 둔다. 카톡 인앱과 외부 브라우저는 저장소가 따로라서 주소에 담는다. 주소의 id가 이 작품의 댄서가 아니면 "선택 안 함"으로 처리한다.
- **팀 파일 자체.**
- **아직 서버에 올리지 못한 변경:** 서버가 아니라 기기 저장소에 둔다(§7.2).

### 5.5 형식 변경과 확장

- **표 구조를 바꿀 때:** Flyway 마이그레이션을 쓴다. 첫 배포 이후에는 파괴적 변경을 금지한다(add → copy → drop 순서로 한다).
- **문서 형식을 바꿀 때:**
  - 형식 번호 `v`는 문서 안에 있으므로 문서와 함께 다닌다.
  - 서버는 문서를 **읽을 때와 받을 때(POST·PUT) 모두** `v`를 보고 판 올림 함수로 최신 판까지 올린다. 그다음 검증하고 저장한다. 판 올림은 원시 JSON 단계에서 하고, 그 뒤에 최신 판 DTO로 바인딩한다.
  - 프론트는 자기가 아는 판보다 높은 `v`를 받으면 편집을 막고 새로고침을 안내한다.
  - 판 올림 함수마다 테스트를 둔다.
- **나중에 붙일 것 (지금은 만들지 않는다):**
  - 대형 이름·메모·색: 문서의 선택 필드로 추가한다.
  - 편집자(S-01): `app.project_editor(project_id, user_id)` 표를 붙인다.
  - 편집 잠금: `project`에 칸 2개를 추가한다.
  - v2 동아리: `app.team` 표와 `project.team_id`(nullable)를 붙인다.

## 6. API 계약

`contract/openapi.yaml`이 원본이다. `content` 문서의 스키마(§5.3의 범위, 길이, 개수)도 여기에 적는다. 오류는 RFC 9457 Problem Details(`application/problem+json`)로 돌려준다.

| 누가 | 요청 | 응답 |
|---|---|---|
| 리더 | `GET /api/projects` | 200 `[{id, title, updatedAt, dancerCount, formationCount, durationMs}]`. 최근 수정순이다. `durationMs`는 `teamFile.durationMs` 또는 null이다 |
| 리더 | `POST /api/projects` `{title, content}` | 201 `{id, revision: 1, shareToken}` |
| 리더 | `GET /api/projects/{id}` | 200 `{id, title, revision, content, shareToken}` |
| 리더 | `PUT /api/projects/{id}` `{baseRevision, content}` | 200 `{revision}` / **409** `{revision, content}` (최신본) |
| 누구나 | `GET /api/share/{token}` | 200 `{title, ownerName, content}` |
| 운영 | `GET /api/health` | 200. DB를 실제로 한 번 조회한다 |

**규칙**

1. **인증:** 리더 요청에는 `Authorization: Bearer <Supabase access token>`을 붙인다. 토큰이 없거나 틀리면 401이다.
2. **권한:** 모든 작품 쿼리에 `owner_id = JWT sub` 조건을 건다. 남의 작품이거나 없는 작품이면 **404**를 돌려준다(403이 아니다. 존재 여부를 숨긴다).
3. **사용자 등록:**
   - `POST /api/projects`를 처리할 때 `app_user`를 upsert한다. 가입 API는 따로 두지 않는다.
   - `display_name`은 JWT의 `user_metadata`에 있는 닉네임에서 읽는다. 키 이름은 SP-4에서 확정하고, 후보는 `name`이다.
   - 이 값은 사용자가 바꿀 수 있으므로 trim한 뒤 20자로 자른다. 비어 있으면 "리더"로 저장한다.
4. **작품 만들기:**
   - 첫 문서는 프론트가 만든다. `v: 1`, 댄서 0명, 대형 1개(0ms, positions 비어 있음), tempo와 teamFile은 null이다.
   - 서버는 규칙 7과 같은 검증을 한다.
   - 소유자의 작품이 이미 50개면 400(Problem type `project-limit`)이다.
5. **자동 저장:** 받은 문서의 판을 올리고(§5.5) 검증한 뒤, `UPDATE app.project SET content=?, revision=revision+1, updated_at=now() WHERE id=? AND owner_id=? AND revision=?` 한 문장으로 처리한다. 저장하는 `content`는 판 올림을 마친 받은 JSON 그대로다. DTO는 검증에만 쓰고, 다시 직렬화해 저장하지 않는다. 바뀐 줄이 0개면 한 번 더 읽어서 다음 순서로 판단한다. "같으면" 판정은 DB에서 `content = ?::jsonb`로 한다.
   - 작품이 없거나 남의 것이면 → 404
   - 서버의 `content`가 보낸 것과 JSON 값으로 **같으면** → 200과 현재 revision (응답이 유실된 뒤 재시도한 경우)
   - 그 밖의 경우 → 409와 최신 `{revision, content}`
6. **덮어쓰기(E2):** 409 응답으로 받은 revision을 `baseRevision`으로 삼아 다시 PUT한다. 강제 옵션은 두지 않는다.
7. **검증:**
   - 요청 본문 크기는 Caddy(`request_body max_size 1MB`) 한 곳에서만 검사한다. 넘으면 413이다.
   - 본문이 **§5.3의 모든 규칙**(범위, 정수, 개수, id 유일성, 순서, 겹침 제약, positions 키 = dancers id 집합)을 지키지 않으면 400이다.
8. **공유 조회:** 인증 없이 받는다. 토큰이 없으면 404이며, "없는 토큰"과 "바뀐 토큰"을 구분하지 않는다. 요청 수 제한은 §9.3을 따르고, 넘으면 429다.
9. **나중에 붙일 것 (Should):** `DELETE /api/projects/{id}`(S-19), `POST /api/projects/{id}/share-token`(S-13), 편집자와 잠금(S-01), OG용 `/s/{token}` HTML(S-08).

## 7. 핵심 흐름과 규칙

### 7.1 리더 로그인·로그아웃

1. **로그인:** 카카오 로그인을 누르면 Supabase를 거쳐 앱으로 돌아온다. 토큰 갱신은 supabase-js가 한다.
2. **받는 정보:** 앱 DB(`app` 스키마)에는 **닉네임만** 둔다.
   - Supabase 카카오 공급자는 이메일과 프로필 사진 권한도 항상 요청할 수 있다. SP-4에서 확인한다.
   - 그렇다면 카카오 앱을 "개인 개발자 비즈 앱"으로 전환한다. 닉네임은 필수 동의, 이메일과 프로필 사진은 선택 동의로 둔다. Supabase에서 "Allow users without an email"을 켠다.
   - 이때 Supabase Auth에 저장되는 항목은 처리방침에 모두 적는다(§9.4).
3. **로그인 상태 공유:** 카톡 인앱 브라우저와 외부 브라우저는 로그인 상태를 공유하지 않는다. 환경을 바꾸면 다시 로그인해야 한다.
4. **로그아웃:** ①의 👤 메뉴 → [로그아웃] → `supabase.auth.signOut()`을 부른다. 기본값이 global이라 다른 기기의 세션도 끊는다.
   - 이 탭에 쓰기 실패 중이면서 보낼 것(`pending` 또는 `lastSent`)이 남은 저장 장치가 있으면, 먼저 "아직 저장되지 않은 변경이 있어요. 로그아웃하면 사라져요"를 확인받는다. [취소]를 누르면 ①에 머문다. 빌린 기기일 수 있으므로 로그아웃을 막지는 않는다.
   - `error`가 돌아오면 L0로 보내지 않는다. ①에 머물며 "로그아웃하지 못했어요. 인터넷 연결을 확인하고 다시 눌러 주세요"를 띄운다.
   - 성공하면 `location.replace`로 L0를 새로 불러온다. 저장 장치의 메모리, 타이머, 편집권이 모두 사라진다. `SIGNED_OUT`으로 L0에 갈 때도 같다.
   - 기기 저장소의 미전송 변경은 지우지 않는다. 키가 사용자별이라 다른 계정이 건드리지 않고, 같은 계정으로 다시 로그인하면 §7.2로 복구한다.
   - 이미 발급된 access token이 만료될 때까지(최대 1시간) 유효한 것은 허용한다.

### 7.2 편집과 자동 저장

#### 7.2.1 원칙과 자료

- **선기록:** 편집은 서버보다 **기기 저장소(localStorage)에 먼저** 기록한다. 원본은 서버이고, 기기 저장소는 서버에 올리기 전까지의 임시 보관이다.
- **저장 장치:** 작품마다 하나씩, **앱 수준**에 둔다. 디바운스, 재시도, 숨김 처리는 에디터 화면이 아니라 저장 장치가 한다.
  - 에디터를 떠나도 대기 중인 저장은 이어진다.
  - 같은 탭에서 그 작품을 다시 열면 기존 저장 장치를 이어 쓴다.
- **편집권 (Web Locks `kickoff:project:{projectId}`):**
  - **PUT을 보내는 것과 기기 저장소 항목을 쓰거나 지우는 것은 편집권을 쥔 저장 장치만 한다.**
  - 저장 장치는 두 경우에 편집권을 쥔다. 그 작품의 에디터가 열려 있을 때, 그리고 보낼 것이 남아 있을 때다. 둘 다 아니거나, 에디터가 닫힌 채로 멈춤 상태(E2, 저장 불가)가 되면 편집권을 놓는다.
  - 다른 창이 편집권을 빼앗으면 A13으로 처리한다.
- **기기 저장소 항목:**
  - 키는 사용자와 작품마다 하나다: `kickoff:pending:{userId}:{projectId}`(userId = JWT sub). 그래서 다른 계정의 항목은 보내지도 지우지도 않는다.
  - 값은 `{baseRevision, content, lastSent}`다.
  - `lastSent`는 보냈지만 결과를 아직 모르는 본문이고, 없으면 `null`이다.
  - 결과를 모르는 요청이 있으면, 다음 전송은 **그 본문을 같은 base로 다시 보내서** 결과부터 확정한다. 이미 반영된 요청이었다면 서버는 "같은 내용이면 200"(§6 규칙 5)으로 답한다. 그래서 응답이 유실돼도, **그 사이 다른 기기가 저장하지 않았다면** 자기 저장을 충돌로 착각하지 않는다. 다른 기기가 저장한 경우는 §7.2.6에서 다룬다.
- **쓰기 실패:** 기기 저장소 쓰기가 실패하면(용량 초과 등, 어느 단계에서든) 그 작품의 항목을 **지운다.** 옛 content가 남으면, 나중에 새 base가 붙어 서버본을 되돌릴 수 있기 때문이다.
  - 편집은 막지 않고, 디바운스 없이 바로 보낸다(A2). A2 안의 기록이 실패했으면 항목만 지우고 그 PUT은 그대로 보낸다.
  - "쓰기 실패" 배너를 띄운다: "이 변경은 아직 어디에도 저장되지 않았어요. 연결될 때까지 창을 닫지 마세요". 이 배너가 떠 있는 동안에는 E3 배너 대신 이것을 보여 준다.
  - 다음 쓰기가 성공하거나 상태가 저장됨이 되면(A3·A4(a)·A5) 배너를 지운다.
- **메모리 (작품별):** 현재 문서, `baseRevision`, `lastSent`, `pending`(서버에 아직 반영되지 않은 변경이 있음), 요청 진행 여부, 상태.
- **비교:** 문서 비교는 모두 **JSON 값 비교**다. 문자열로 비교하지 않는다.
- **한 번에 요청 1개:** 저장 요청은 한 작품에 **한 번에 1개**만 보낸다. keepalive 전송과 §7.2.5의 전송도 여기에 포함된다.

#### 7.2.2 상태

| 상태 | 화면 표시 | 편집 |
|---|---|---|
| 저장됨 | "저장됨 ✓" | 가능 |
| 대기·전송 중 | "저장 중…" | 가능 |
| E3 연결 끊김 | E3 배너 (쓰기 실패 중이면 쓰기 실패 배너) | 가능 (선기록은 계속) |
| E2 충돌 | E2 대화상자 | **멈춤** |
| 저장 불가 | 저장 불가 배너 | **멈춤** |
| 다른 창에서 열림 | 다른 창 안내 | **멈춤** |

**멈춤인 세 상태**(E2, 저장 불가, 다른 창에서 열림)에서는 그 작품의 A2를 부르지 않는다. 디바운스, E3 재시도, `online`, A11, A12가 모두 해당한다. 기기 저장소 항목은 그대로 두고, 다시 열 때 §7.2.4가 처리한다.

#### 7.2.3 이벤트와 동작 (이 표가 §8 자동 저장 단위 테스트 목록이다)

| # | 이벤트 | 동작 |
|---|---|---|
| A1 | 편집 (문서가 **실제로 바뀐** 경우만. 같은 값을 다시 넣는 것은 편집이 아니다) | `pending = true`. 기기 저장소에 `{baseRevision, content: 현재 문서, lastSent}`를 쓰고 1초 디바운스를 다시 시작한다. 쓰기가 실패하면 §7.2.1을 따른다 |
| A2 | 보낼 때 (디바운스 끝, A3의 후속 전송, E3 재시도, `online`, A11, A12) | 다음 중 하나면 아무것도 하지 않는다: 멈춤 상태, 요청이 돌고 있음(A3에서 이어 보낸다), **`pending`도 `lastSent`도 없음**(보낼 것이 없다). 그 밖이면 본문을 정한다. `lastSent`가 있으면 **그 본문**(결과 확정용), 없으면 **현재 문서**다. 본문을 `lastSent`로 두고 기기 저장소에도 기록한 뒤 `PUT {baseRevision, content: 본문}`을 보낸다 |
| A3 | 200 `{revision}` | `baseRevision = revision`, `lastSent = null`. 현재 문서가 보낸 본문과 같으면 `pending = false`, 기기 저장소 항목을 지우고 "저장됨 ✓". 다르면(요청 중에 편집이 있었거나 결과 확정용 전송이었으면) 항목을 `{새 base, 현재 문서, null}`로 고쳐 쓰고 바로 A2 |
| A4 | 409 `{revision, content}` | `lastSent = null`. (a) 서버 content가 현재 문서와 같으면 `baseRevision = revision`, `pending = false`, 항목을 지우고 "저장됨 ✓". (b) 그 밖이면 **E2** |
| A5 | E2 [최신 버전 불러오기] | 현재 문서 = 서버 content, `baseRevision = revision`, `pending = false`, 기기 저장소 항목을 지운다. 대기 중인 저장과 타이머는 버린다 |
| A6 | E2 [내 변경으로 덮어쓰기] | "다른 기기에서 저장한 내용이 사라져요"를 확인받은 뒤 `baseRevision = revision`, 바로 A2(현재 문서) |
| A7 | 400 · 413 | 보낸 본문이 반영되지 않은 것이 확정됐다. `lastSent = null`로 두고 항목에도 반영한다. 보낸 본문이 결과 확정용이었고 현재 문서와 다르면 바로 A2를 **한 번** 한다(현재 문서). 그 밖이면 **저장 불가**다. 재시도하지 않고 항목은 남긴다. [서버 버전 불러오기]를 누르면 `GET /api/projects/{id}`의 `{revision, content}`로 A5를 한다. GET이 실패하면 조회 실패 안내를 띄우고 상태는 그대로 둔다. 저장 불가는 클라이언트 버그의 신호다 |
| A8 | 401 | `lastSent`는 그대로 둔다. supabase-js로 세션을 한 번 갱신하고 A2를 다시 한다. 세션이 무효(`SIGNED_OUT`)면 L0로 보낸다(§7.1). 기기 저장소 항목은 그대로 둔다. 네트워크 때문에 갱신이 실패하면 A10으로 처리한다. 갱신한 뒤 다시 보낸 PUT도 401이면 A10으로 처리한다. 갱신을 기다리는 동안은 '요청이 돌고 있음'으로 본다 |
| A9 | 404 | 기기 저장소 항목(현재 사용자의 키)을 지운다. 에디터에 있으면 "작품을 찾을 수 없어요"를 띄우고 ①로 간다 |
| A10 | 네트워크 오류 · 5xx · 시간 초과(보낸 뒤 15초, `AbortSignal.timeout`) | **E3.** 편집은 계속된다(A1). `lastSent`는 그대로 둔다(결과를 모르기 때문). `online` 이벤트 또는 10초마다 A2 |
| A11 | `pagehide` 또는 `visibilitychange` hidden | A2의 조건을 만족하고, 요청이 돌고 있지 않고, 본문이 60KB 이하이면 `fetch(..., {keepalive: true})`로 A2를 한다(keepalive 요청은 64KB 제한이 있다). 응답이 오면 A3·A4 등과 똑같이 처리한다 |
| A12 | 에디터를 떠남(← 포함) | 디바운스를 기다리지 않고 바로 A2. 화면 이동은 응답을 기다리지 않는다 |
| A13 | 편집권 빼앗김 (`AbortError`) | 이 창에서 그 작품의 저장 장치를 끈다. 타이머를 취소하고, 이후 도착한 응답은 무시하고, 기기 저장소를 **쓰지도 지우지도 않는다.** 에디터가 열려 있으면 "다른 창에서 열림"을 띄운다. 남은 변경은 새 창이 §7.2.4 3번으로 이어받는다. 쓰기 실패 중이던 변경은 이어받을 수 없다(§7.2.6) |

**에디터가 열려 있지 않은 작품의 결과**(①이나 다른 작품의 ③에 있을 때 도착한 응답)는 화면에 띄우지 않고 화면도 옮기지 않는다.
- A4(b)·A7이면 항목을 남기고 그 작품의 저장 장치를 멈춘다(편집권도 놓는다).
- A9면 항목만 지운다.
- 그 작품을 열 때 §7.2.4로 다시 처리한다.

#### 7.2.4 작품을 열 때

1. **저장 장치와 편집권:**
   - 이 탭에 그 작품의 저장 장치가 살아 있으면(편집권을 쥐고 있으면) 그것을 이어 쓴다. content는 저장 장치의 현재 문서를 쓰고, 2번의 GET은 제목 같은 나머지 정보만 받는다.
   - 저장 장치가 없으면 `navigator.locks.request('kickoff:project:' + id, {steal: true}, …)`로 편집권을 가져와 새 저장 장치를 만든다. **나중에 연 창이 이긴다.**
2. **서버본:** `GET /api/projects/{id}`. 404면 A9, 401이면 §7.6 "로그인 만료", 그 밖의 실패면 조회 실패 화면(§7.6)이다.
3. **남은 변경 복구:** 현재 사용자의 기기 저장소에 이 작품의 항목이 있으면, 현재 문서·`baseRevision`·`lastSent`를 항목 값으로 두고 `pending = true`로 한 뒤 **바로 A2**를 한다. 결과는 §7.2.3을 따른다. 클라이언트가 revision을 직접 비교해 E2를 띄우는 분기는 없다.
4. **새로 시작:** 항목이 없으면 서버본으로 시작한다.

#### 7.2.5 앱을 열 때 (①)

- 현재 사용자의 `kickoff:pending:{userId}:*` 항목마다, 그 작품의 편집권이 비어 있으면(`locks.request(…, {ifAvailable: true})`) 그 편집권을 쥔 저장 장치를 만들고 A2~A4 규칙대로 보낸다. 결과 확정용 전송이 있으면 한 항목에 최대 2번이다.
- 결과는 "에디터가 열려 있지 않은 작품의 결과" 규칙(§7.2.3 아래)을 따른다. 그래서 ①에는 E2가 뜨지 않는다.
- 전송 중에 리더가 그 작품을 열면 §7.2.4 1번에 따라 같은 저장 장치를 이어 쓴다.

#### 7.2.6 알아 둘 한계

- **기기 저장소는 지워질 수 있다.** iOS는 사이트를 7일 동안 쓰지 않으면 저장소를 지울 수 있다. Safari 탭, 홈 화면 앱, 카톡 인앱은 저장소를 공유하지 않는다. 그래서 E3 문구가 "이 브라우저로 다시 열어 달라"고 안내한다.
- **오래 열어 둔 탭은 최신본을 자동으로 받지 않는다.** 다른 기기에서 저장한 뒤 이 탭에서 편집하면 E2가 뜬다.
- **응답이 유실된 저장 뒤에 다른 기기가 저장하면 가짜 E2가 뜬다.** 유실된 저장은 사실 반영됐고, 그 위에 다른 기기가 저장한 경우다. 이 기기에 새 변경이 없어도 E2가 뜬다. 서버에 판 이력이 없어 진짜 충돌과 구분하지 못하기 때문이다. 그래서 E2 대화상자에 "다른 기기의 최신 버전에 이 기기의 변경이 이미 들어 있을 수 있어요. 덮어쓰기 전에 다른 기기에서 확인하세요"를 함께 적는다. 파일럿에서 실제로 문제가 되면 저장 id 기록을 도입한다.
- **쓰기 실패 중의 변경은 이 창의 메모리에만 있다.** 이 창을 닫거나 새로 불러오면(로그아웃, `SIGNED_OUT` 포함), 또는 다른 창에서 같은 작품을 열면 사라진다. 그래서 쓰기 실패 배너가 "창을 닫지 마세요"라고 안내하고, 로그아웃은 확인을 받는다(§7.1).

### 7.3 편집 규칙

- **선택 대형:**
  - 선택 대형은 `startMs ≤ t`인 마지막 대형이다(t = 플레이헤드). 정지 상태에서 스크럽할 때도 바로 바뀐다.
  - [삭제]는 선택 대형을 지운다. 확인 창은 "대형 N을 지울까요?"라고 묻는다. 첫 대형은 지울 수 없어 버튼이 꺼진다.
  - [+대형]을 누르면 플레이헤드가 새 대형의 startMs로 옮겨 간다.
- **이동 구간 잠금:** 다음 대형 G의 이동 구간(`G.startMs − G.transitionInMs ≤ t < G.startMs`)에 플레이헤드가 있으면 무대 편집을 잠그고 [삭제]도 끈다(무대에 보이는 것과 지워질 대형이 다르기 때문이다). 이전 앱과 같다.
- **재생 중 잠금:** 재생 중에는 무대·타임라인 편집과 [+대형]·[삭제]를 잠근다.
- **댄서 추가:**
  - 최대 50명이고, 50명이면 [+댄서]를 끈다.
  - 새 댄서의 순번 `i` = 추가 전 댄서 수, `s = i mod (2·rows)`로 둔다. 기본 이름은 "댄서 {i+1}"이다.
  - `s < rows`이면 `(0.5/cols, (s+0.5)/rows)`에, 아니면 `(1 − 0.5/cols, (s−rows+0.5)/rows)`에 놓는다.
  - **모든 대형에 같은 좌표**로 넣는다. 칸이 비어 있는지는 판정하지 않는다(겹침 허용).
- **대형 추가:**
  - 최대 200개이고, 200개면 [+대형]을 끈다.
  - 마지막 대형 L을 복사하고, 새 id를 붙인다.
  - 템포가 있으면 `b = beat(L.startMs)`로 두고, `startMs = gridMs(b+8)`, `transitionInMs = gridMs(b+8) − gridMs(b+6)`(2카운트)이다.
  - 템포가 없으면 `startMs = L.startMs + 4000`, `transitionInMs = 1000`이다.
  - 새 startMs가 1,800,000을 넘으면 [+대형]을 끈다.
- **토큰 드래그:** 끄는 동안에는 자유롭게 움직인다. 손을 떼면 **−0.1~1.1 안에 있는** 0.5칸 교차점(x는 `0.5/cols` 간격, y는 `0.5/rows` 간격) 중 가장 가까운 점에 붙는다.
- **타임라인 블록:**
  - 블록을 드래그하면 `startMs`가, 이동 구간 핸들을 드래그하면 `transitionInMs`가 바뀐다.
  - 템포가 있으면 박 격자(`gridMs(k)`)에 붙고, 없으면 100ms 단위(정수)에 붙는다. 1-1 이전 구간도 같은 격자를 쓴다.
  - 붙인 값이 겹침 제약, 엄격한 순서(§5.3), 0~1,800,000 중 하나라도 벗어나면 경계에서 멈춘다(클램프). 이때 값은 격자 밖일 수 있다. 블록의 왼쪽 경계는 `F(n−1).startMs + max(F(n).transitionInMs, 1)`이다.
  - 첫 대형은 블록도 이동 구간 핸들도 움직이지 않는다(startMs=0, transitionInMs=0 고정).
- **정수화:**
  - 문서에 쓰는 모든 시간은 쓰기 직전에 `Math.round`로 정수 ms로 만든다. 격자 시각, 미디어의 `currentTime`·`duration`이 여기에 해당한다.
  - 입력칸의 값은 유효할 때만 문서에 반영한다.
- **템포 입력(④):**
  - BPM은 확정할 때(blur·Enter)만 반영한다. 20~300 밖이면 반영하지 않는다.
  - 빈 값으로 확정하면 `tempo = null`이다.
  - tempo를 새로 만들 때 `firstBeatMs`는 0이다.
  - "지금 위치를 1-1로"는 BPM이 있을 때만 켜지고, `firstBeatMs = Math.round(min(t, 1800000))`이다(t = 플레이헤드, §7.4).
  - **BPM이나 1-1을 바꿔도 대형 ms는 바꾸지 않는다.**
- **작품 끝:** `max(teamFile?.durationMs ?? 0, 마지막 대형 startMs + 4000)`. 에디터와 뷰어 모두 문서의 이 값을 쓴다. 타임라인은 0부터 작품 끝까지 그린다.

### 7.4 재생 엔진 (에디터와 뷰어 공용)

- **팀 파일:**
  - `<input type="file" accept="video/*,audio/*">`로 고른다. `URL.createObjectURL`로 만든 주소를 **`<video playsinline>` 요소 하나**에 넣어 재생한다. 음원 파일도 이 요소로 재생한다.
  - `duration`이 유한하지 않거나 30분을 넘으면 받지 않고 "30분 이하 파일을 골라 주세요"를 띄운다.
- **teamFile 기록:** **에디터에서** 리더가 파일을 고르면, 값이 바뀐 경우에만 문서의 `teamFile{name, durationMs}`를 갱신한다(편집으로 취급해 자동 저장). 뷰어에서 멤버가 고른 파일은 문서를 바꾸지 않는다.
- **플레이헤드와 시계:**
  - 플레이헤드 `t`는 앱 상태이고 0~작품 끝(§7.3) 범위를 가진다.
  - 재생 중에는 `t`를 `video.currentTime`에서 읽는다. 자체 타이머로 시간을 누적하지 않는다.
  - 정지 중 탐색은 `t`를 바꾼다. 파일이 있으면 `currentTime = min(t, duration)`으로 맞춘다. `t ≥ duration`이면 재생 버튼을 끈다.
  - 앵커는 `(currentTime, performance.now())` 쌍이다. currentTime 값이 바뀔 때마다 앵커를 다시 잡고, 그 사이는 `performance.now()`로 보간한다.
  - 정지·탐색 중, 그리고 재생을 시작한 뒤 currentTime 값이 처음 바뀌기 전까지는 외삽하지 않는다(현재 위치에 둔다).
  - 드리프트 처리 기준(ms)은 SP-3 결과로 정한다.
- **그리기:** `requestAnimationFrame`마다 `t`를 읽어 `poseAt(t)`로 위치를 구하고 그린다.
  - 이동 시작 전: 직전 대형 위치를 유지한다.
  - 이동 구간: 직선 경로를 따라 움직이고, 속도 곡선은 easeInOut(`cubic-bezier(0.42, 0, 0.58, 1)`)이다.
  - 마지막 대형 이후: 마지막 대형 위치를 유지한다.
- **Wake Lock (M-14):**
  - 재생을 시작할 때(사용자 탭) `navigator.wakeLock.request('screen')`을 요청한다.
  - 정지하거나 곡이 끝나면 해제한다. 화면이 숨겨지면 브라우저가 자동으로 해제한다.
  - 거부되거나 지원하지 않으면 조용히 넘어간다.
- **백그라운드:** 앱이 백그라운드로 가면(`visibilitychange` hidden) 재생을 멈춘다.
- **파일이 없을 때:** 재생 버튼을 누르면 파일을 고르라고 안내한다. 타임라인 탐색(정지 상태 스크럽 보간)은 파일 없이도 된다.

### 7.5 공유와 멤버 보기

1. **⑤ 공유:** `https://<도메인>/s/{shareToken}`을 복사하거나 `navigator.share`로 보낸다. `navigator.share`가 없으면 복사만 제공한다.
2. **⑥ 링크 첫 화면:** `GET /api/share/{token}`을 부른다. 404면 E1, 그 밖의 실패면 조회 실패 화면이다.
   - User-Agent에 `KAKAOTALK`이 있으면 카톡 인앱 배너를 띄운다. 외부 브라우저로 여는 방법과 문구는 스파이크 결과로 정한다.
3. **⑦ 나는 누구:** 고르면 `history.replaceState`로 `?me=`를 붙인다. 주소에 이미 유효한 `?me=`가 있으면 건너뛴다(§4.2).
4. **⑧ 보기:** 재생과 Wake Lock은 §7.4를 따른다.
5. **최신본:** 뷰어는 연 시점의 최신본을 보여 준다. 자동으로 갱신하지 않고, 새로고침하면 최신이 된다.

## 9. 보안과 개인정보

### 9.1 인증·권한

- **JWT 검증:** Spring Security Resource Server가 Supabase JWKS로 검증한다.
  - 알고리즘을 확인한다. ES256이면 `spring.security.oauth2.resourceserver.jwt.jws-algorithms: ES256`을 설정한다.
  - 발급자(`iss`)와 대상(`aud=authenticated`)도 검증한다.
- **소유자 확인:** 모든 작품 쿼리에 `owner_id` 조건을 건다(§6 규칙 2).

### 9.2 DB·인프라

- **스키마와 역할:** 전용 스키마 `app`을 쓴다. 역할은 둘로 나눈다.
  - Flyway용(DDL 소유자)
  - 앱 실행용(`app` 스키마의 DML만 허용)
  - 역할과 비밀번호는 환경마다 한 번 수동으로 만든다. Flyway에는 권한만 넣는다(§5.2).
- **Supabase Data API:** `app`을 노출하지 않는다. `anon`과 `authenticated` 역할에는 `app` 권한을 주지 않는다. `public` 스키마에도 권한이 걸려 있지 않은지 **셋업할 때 확인 쿼리로 검증한다**(결과 0건).
- **JDBC 연결:** Supabase Session pooler(5432)로 접속한다.
- **CORS:**
  - 운영 API는 운영 웹 주소만 허용한다.
  - 스테이징 API는 스테이징 주소, `https://*.<pages프로젝트>.pages.dev`, `http://localhost:<port>`를 허용한다.
- **Supabase 로그인 후 돌아올 주소:**
  - 운영은 운영 주소만 허용한다.
  - 스테이징은 `https://*.<pages프로젝트>.pages.dev/**`와 `http://localhost:<port>/**`를 허용한다.
- **비밀값:**
  - 저장소에 넣지 않는다.
  - 배포 SSH 키와 E2E 테스트 계정은 저장소 시크릿이 아니라 **GitHub Environment `deploy`**의 시크릿에 둔다. 배포 브랜치는 `develop`·`main`으로 제한한다. 그래서 PR 워크플로에는 전달되지 않는다.
  - 저장소 수준 시크릿은 `CLAUDE_CODE_OAUTH_TOKEN` 하나뿐이다.
  - DB와 S3 자격증명은 VM 환경변수에만 둔다.
  - 공개 레포의 push protection을 켠다.

### 9.3 공유 링크·입력

- **공유 토큰:** `SecureRandom` 16바이트 이상을 base64url로 인코딩한다. 보기 전용이고 리더가 다시 봐야 하므로 평문으로 저장한다.
- **유출 대응 (파일럿 중 수동):** 리더가 요청하면 운영자가 해당 작품의 `share_token`을 새 무작위 값으로 UPDATE하고, 새 링크를 리더에게 전한다. 옛 링크는 E1이 된다. 기능으로 만드는 것은 S-13이다.
- **요청 수 제한:**
  - `/api/share/*`에 클라이언트 IP당 **분당 300회**를 건다. 학교 와이파이 NAT와 통신사 CGNAT에서는 여럿이 IP 하나를 쓰기 때문이다.
  - 클라이언트 IP는 `server.forward-headers-strategy: native`로 얻고, `X-Forwarded-For`를 직접 파싱하지 않는다. Caddy의 `trusted_proxies`는 기본값을 유지한다. API 도메인은 Cloudflare 프록시를 끈다(§3.1).
  - 서버가 1대라 메모리 카운터로 충분하다. 서버를 늘리면 공용 저장소로 옮긴다.
- **작품 수 상한:** 리더 한 명당 50개(§6 규칙 4). 무료 DB 용량(500MB)을 한 계정이 채우지 못하게 한다.
- **검색 비노출:** Cloudflare Pages `_headers`에 `/s/*` → `X-Robots-Tag: noindex`를 넣는다. robots.txt로 `/s/`를 막지 **않는다**. 막으면 크롤러가 noindex를 읽지 못해 주소만 검색에 오를 수 있기 때문이다.
- **출력:** 사용자 문자열(제목, 이름)은 React 기본 escape로만 출력하고, `dangerouslySetInnerHTML`은 금지한다. S-08 OG HTML에서는 따로 escape한다.

### 9.4 개인정보

- **이용 대상:** 만 14세 이상이다. L0 버튼 아래와 처리방침에 한 줄로 적는다. 연령 확인 기능은 만들지 않는다.
- **처리하는 항목:**
  - **리더 계정:**
    - 필수: 카카오 회원번호, 닉네임.
    - 카카오가 제공하고 리더가 동의한 경우: 이메일, 프로필 사진 URL. Supabase Auth에 저장되고, 앱 DB에는 닉네임만 둔다(§7.1).
  - **접속 기록:** IP, 브라우저 정보. Supabase Auth가 기록한다. API 서버는 요청 수 제한 때문에 IP를 메모리에서만 쓴다.
  - **리더가 입력한 내용:** 작품 내용과 댄서 이름. **공유 링크를 가진 누구에게나 제목, 리더 닉네임, 댄서 이름이 보인다.** ⑤에서 별명을 써도 된다고 안내한다.
  - **팀 파일:** 서버로 보내지 않는다.
- **처리방침(M-17):**
  - 개인정보보호위원회의 처리방침 작성지침에 있는 필수 기재 항목을 따른다. 처리 목적, 항목, 보유 기간과 파기(백업은 30일 보관 뒤 자동 삭제되므로 탈퇴 뒤에도 최대 30일 남는다), 처리 위탁(Supabase, AWS, Cloudflare), 국외 이전 해당 여부(서울 리전 확인), 정보주체의 권리와 행사 방법(탈퇴·열람 요청 이메일과 처리 기한), 안전성 확보 조치, 보호책임자 연락처를 모두 적는다.
  - 문구는 구현할 때 실제 스키마, Supabase Auth, 백업에 저장되는 항목과 대조해 쓴다.
- **회원 탈퇴(S-22):** 파일럿 중에는 요청이 오면 수동으로, 이 순서로 처리한다.
  1. `auth.identities`에서 카카오 회원번호(provider_id)를 조회한다.
  2. 카카오 서비스 앱 어드민 키로 `/v1/user/unlink`(target_id_type=user_id)를 부른다. 어드민 키는 저장소와 서버에 두지 않고 운영자만 보관한다.
  3. `app_user`를 삭제한다(작품도 cascade로 삭제된다).
  4. Supabase 사용자를 삭제한다.
- **백업:** 매일 `pg_dump -n app`을 떠서 비공개 S3에 두고, 30일 뒤 자동 삭제한다(§3.2). 실제 사고 때 복원 대상은 같은 Supabase 프로젝트다(auth는 Supabase가 관리한다). **복원 연습은 M1에서 스테이징 DB에 한 번 한다**(그때 운영에는 실사용자가 없다).

## 12. 열린 항목

- **서비스 이름:** M0 셋업 전에 정한다.
- **파일럿 시점:** 사용자가 동아리의 겨울방학 연습 일정을 확인한다.
- **카카오 비즈 앱 전환:** SP-4에서 필요하다고 나오면, 사용자가 본인인증을 거쳐 "개인 개발자 비즈 앱"으로 전환한다.
- **OG 미리보기 렌더링 위치(S-08):** Cloudflare Pages Function 또는 Spring. 착수할 때 정한다. Pages Function이면 `_headers`가 적용되지 않으므로 `X-Robots-Tag`를 함수 응답에 직접 넣는다.
- **gh 토큰:** 셋업할 때 사용자가 `gh auth refresh -s project`를 실행한다.

## 13. ADR 후보 (레포를 만든 뒤 기록)

1. 웹앱(PWA) 하나로 만든다. Flutter가 아니다.
2. 음원과 영상은 각자 기기의 로컬 파일을 쓰고 서버에 두지 않는다(저작권). 앱은 파일을 구하는 경로를 안내하지 않는다.
3. 백엔드는 Spring Boot로 직접 만들고, Supabase는 Auth와 DB 호스팅만 쓴다.
4. 모노레포로 하고, 계약을 먼저 정한다(OpenAPI). 계약에서 코드를 생성한다.
5. 데이터 모델은 하이브리드로 한다: 표 + JSONB 문서, 낙관적 잠금, 형식 번호는 문서 안의 `v`.
6. 간소화 Git Flow와 보호 규칙: develop은 squash, main은 merge commit.
7. 범위 판정 기준: "최대한 덜어내라", 완료 시나리오 기준.
8. 자동 저장은 선기록 + 상태 표(§7.2)로 한다. 결과를 모르는 요청은 같은 본문으로 다시 보내 확정한다(서버의 "같은 내용이면 200"). 한 작품의 편집권은 Web Locks로 한 창의 저장 장치에만 주고, 편집권을 쥔 저장 장치만 보내고 기기 저장소를 바꾼다. 기기 저장소 키는 사용자별이다.
